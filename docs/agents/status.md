# Status and roadmap

What is built, what is live, and what is left, phase by phase. `docs/index.md`
is the design and the plan; this file is how far it has got. `verifying.md`
beside it is the runbook: what runs on the cluster right now and how to check
it. `AGENTS.md` at the repo root has the rules for working here.

**Keep it current.** A change that alters a fact on this page updates the page
in the same pull request. A stale line here is how the next person, or the
next model, goes wrong.

Commit hashes and image tags in the phase notes below say what was live when
that phase shipped. They are history. The image, chart revision and render
command that are live **now** are in `verifying.md`, and the cluster itself is
the final word.

- **Sessions (2026-10-11):** a login becomes a session of Forge's own (`internal/server/sessions.go`, store `internal/store/session*.go`, migration 0004, `AuthService.CreateSession/ListSessions/DeleteSession`, `forge auth session list|revoke`).
  - Why: with GitHub behind Dex a refresh re-checks the person with the GitHub token of that login, and GitHub keeps only the ten newest tokens per person and OAuth app, so ten dashboard sign-ins logged the CLI out (Dex log: `failed to refresh identity ... Bad credentials`).
  - A session token is `fgs_` + 32 random bytes, stored as its SHA-256; `WithSessions` reads it before the OIDC authenticator.
  - CLI sessions end 90 days after their last use (every use, written at most every 5 minutes, starts the 90 days again), web sessions 7 days after the sign-in; the client is decided by the ID token's audience (`OIDCAuthenticator.SetWebClient`), never by the caller.
  - A session is made only from an ID token less than 10 minutes old (`Principal.IssuedAt`), not from a session or a CI token, and needs the GitHub user name (`preferred_username`, scope `profile`) when memberships are checked. forge-api rechecks hourly with its App (`github.Client.OrgMember/TeamMember`, the `memberships` endpoints): out of the organization ends the session, the writer teams (`--writer-groups`) are added or removed, other groups stay as the login gave them; GitHub down keeps the last answer for 24h, asked at most once a minute.
  - One person keeps 30 sessions (the least recently used goes).
  - A login makes one session (`Principal.LoginID`, remembered in memory for the ten minutes).
  - The membership check runs on its own 10s limit, not the request's, and requests that arrive meanwhile wait for its answer; only a failed check starts the one-minute back-off.
  - A session forge-api ends because its person left is in the audit log as `auth.session.end` by `system`.
  - `cmd/forge-api` offers sessions only with the GitHub App (no App, no way to notice someone left), and `GetServerInfo.sessions` tells clients: the CLI then asks for no refresh token, and a new login ends the session the machine had.
  - An API without `Options.Sessions` answers Unimplemented and the CLI keeps ID and refresh tokens.
  - Known limits: a person is checked by GitHub user name, not id; writer groups outside `--github-org` are kept as the login gave them (a warning at start).
- **Versions (2026-10-11):** forge-api gives every deployed commit a version in the service's repo (`internal/server/release.go`, maths in `internal/semver`, GitHub calls in `internal/github/releases.go`; on when `DeployOptions.Releases` is set, which `cmd/forge-api` always does with deploys).
  - A staging deploy cuts a candidate `vX.Y.Z-rc.N` after the image exists (step `release`, GitHub pre-release); a promotion or a deploy straight to production cuts the final `vX.Y.Z` on the same commit (`bump` on `PromoteDeployRequest`/`StartDeployRequest`, default patch; Latest; notes since the last final).
  - A commit keeps a version it has, so redeploys and re-promotions cut nothing and every step can be repeated.
  - The version is recorded in the values file (`forge.version`) and the deploy commit (`Forge-Version` trailer), so rollbacks and history carry it; `Deployment.version` for staging shows production's final version while both run the same commit.
  - Pods still run `:<sha7>`; the templates' `release.yml` (on a `v*` tag) adds the version tag to that image.
  - Tags that are not `vX.Y.Z` or `vX.Y.Z-rc.N` are ignored.
  - The tag is the version, so a deploy fails with `release_failed` before it changes anything when the tag cannot be made; the GitHub release is best effort (the `release` step says when it could not be made, and the next deploy of the commit makes it).
  - A staging deploy never makes the release of a final version, and `bump` is refused outside production.
  - Versions are cut under one lock per repo.
  - Known limit: the tag list is read in full on every deploy and refuses a repo with more than 5000 tags (`github.ErrTooManyTags`) rather than work from a partial list; prune old `-rc` tags or change the lookup before a service gets there.
  - Forge itself is released by pushing a `vX.Y.Z` tag to `showmino/forge` (`release.yml`, goreleaser: CLI binaries and `ghcr.io/showmino/forge-api:vX.Y.Z`).
- **Deleting a service (2026-10-11):** `DeleteService` takes down what the service runs before it leaves the catalog (`internal/server/service_teardown.go`, wired with `catalog.EnableTeardown`): previews are destroyed, then production and staging are removed (the values file leaves forge-deploys, Argo CD removes the application and its workloads, forge-api deletes the namespace if it is Forge's), and the catalog entry goes last.
  - With anything to take down it is an operation of kind `delete_service` on `services/<svc>`; a service that runs nothing is removed at once.
  - While it runs the service is marked as being deleted (`Catalog.refuseDeleting`): no deploy, preview or resource run can start for it, and its deploy targets are locked.
  - It never touches a namespace or an Argo CD application without Forge's labels, keeps the GitHub repo, and every step can be repeated, so a failed or cancelled delete is run again; a cancel after the values left the deploy repo says that Argo CD still takes the service down.
  - `validate_only` returns what would be taken down (`removes`), which the CLI prints before it asks.
