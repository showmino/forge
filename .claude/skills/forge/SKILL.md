# Forge

Forge is an internal developer platform: the `forge` CLI, the `forge-api` server and
the Protobuf contract they share, in one Go module (`github.com/showmino/forge`).
The approved design doc is `docs/index.md` (command surface, auth, API, output
and exit codes, phases with exit gates, open questions): read the relevant
section before designing anything. README.md has the user-facing docs; this
skill holds what neither says.

## Decisions (settled; do not reopen without the owner)

- ConnectRPC, not grpc-gateway. One Go module.
- Dex for local and demo login; production IdP deferred. CLI uses the OIDC device flow and sends the **ID token** as bearer; the API verifies it with the CLI client ID (`forge-cli`) as audience.
- Argo CD only (Flux later). OpenTofu jobs run by the API (not Crossplane).
- Templates live in a Git repo, versioned by tag.
- The Phase 6 web dashboard is a Next.js app from Forge's own `nextjs` template, deployed by Forge; it is a thin client of the same ConnectRPC API (no dashboard-only endpoints).
- Telemetry off. Distribution: GitHub Releases + Homebrew tap (`showmino/homebrew-tap`).
- Demos run on the owner's k3s cluster (see verifying.md for its quirks).

## Conventions

| Rule | Where it lives |
| --- | --- |
| `forge <noun> <verb>`, one file per noun | `internal/cli/<noun>.go`, registered in `NewRoot` (`root.go`) |
| No package globals; commands get everything via `Deps` (wrapped by `*Factory`) | `internal/cli/factory.go` |
| Commands return errors; only `main` picks exit codes | `internal/exitcode` (`exitcode.New`, `Usagef`); `cli.Run` classifies Connect codes |
| Every command supports `-o table\|json\|yaml\|name`; JSON is the resource itself | `output.Print(w, format, output.View{Headers, Rows, Names, Data})` |
| Golden tests for output | `internal/output/testdata/*.golden`; `make update-golden` after an intended change |
| CLI tests run the real command tree against an in-process API | `newHarness(t)` in `internal/cli/cli_test.go` (static tokens `t-writer`, `t-reader`) |
| Protos in `proto/forge/v1`, AIP-style names (`services/{id}`), `request_id`, `validate_only`, etags | regenerate with `make generate`; `gen/` is committed and CI checks it |
| A resource run (plan or apply) ends through `Resources.endRun`, which changes the plan once and appends the one outcome event | Operations started with `withoutOutcome(ctx)`; never append a resource outcome anywhere else |
| Policy rules are `policy/*.rego`, package `forge.resources`, built into the binary | `policy.New`; every rule has a passing and a failing case in `policy/policy_test.go` |
| Server permissions are strings checked per RPC | `require(ctx, PermX)` in `internal/server/authn.go` |
| Every write RPC is in auditActions, every read in auditReads (TestAuditCoversEveryProcedure) | internal/server/audit.go |

Adding an RPC: edit proto, then `make generate`, then the handler in `internal/server` (register it in `server.New`), then the client in `pkg/client`, the CLI noun, and harness tests; classify it in `auditActions` (a write, with its allowlisted details) or `auditReads`. Run `make test lint` before every commit (TDD: test first).

## Quick reference

```sh
export PATH=$HOME/.local/go/bin:$HOME/go/bin:$PATH   # Go is not on the system PATH
make build test lint                                 # Go 1.27, golangci-lint v2.14.0, as CI
make generate | make update-golden | make api-dev     # api-dev: token "dev", no IdP
```

- **Sessions (2026-10-11):** a login becomes a session of Forge's own (`internal/server/sessions.go`, store `internal/store/session*.go`, migration 0004, `AuthService.CreateSession/ListSessions/DeleteSession`, `forge auth session list|revoke`). Why: with GitHub behind Dex a refresh re-checks the person with the GitHub token of that login, and GitHub keeps only the ten newest tokens per person and OAuth app, so ten dashboard sign-ins logged the CLI out (Dex log: `failed to refresh identity ... Bad credentials`). A session token is `fgs_` + 32 random bytes, stored as its SHA-256; `WithSessions` reads it before the OIDC authenticator. CLI sessions end 90 days after their last use (every use, written at most every 5 minutes, starts the 90 days again), web sessions 7 days after the sign-in; the client is decided by the ID token's audience (`OIDCAuthenticator.SetWebClient`), never by the caller. A session is made only from an ID token less than 10 minutes old (`Principal.IssuedAt`), not from a session or a CI token, and needs the GitHub user name (`preferred_username`, scope `profile`) when memberships are checked. forge-api rechecks hourly with its App (`github.Client.OrgMember/TeamMember`, the `memberships` endpoints): out of the organization ends the session, the writer teams (`--writer-groups`) are added or removed, other groups stay as the login gave them; GitHub down keeps the last answer for 24h, asked at most once a minute. One person keeps 30 sessions. An API without `Options.Sessions` answers Unimplemented and the CLI keeps ID and refresh tokens.
- **Versions (2026-10-11):** forge-api gives every deployed commit a version in the service's repo (`internal/server/release.go`, maths in `internal/semver`, GitHub calls in `internal/github/releases.go`; on when `DeployOptions.Releases` is set, which `cmd/forge-api` always does with deploys). A staging deploy cuts a candidate `vX.Y.Z-rc.N` after the image exists (step `release`, GitHub pre-release); a promotion or a deploy straight to production cuts the final `vX.Y.Z` on the same commit (`bump` on `PromoteDeployRequest`/`StartDeployRequest`, default patch; Latest; notes since the last final). A commit keeps a version it has, so redeploys and re-promotions cut nothing and every step can be repeated. The version is recorded in the values file (`forge.version`) and the deploy commit (`Forge-Version` trailer), so rollbacks and history carry it; `Deployment.version` for staging shows production's final version while both run the same commit. Pods still run `:<sha7>`; the templates' `release.yml` (on a `v*` tag) adds the version tag to that image. Tags that are not `vX.Y.Z` or `vX.Y.Z-rc.N` are ignored. The tag is the version, so a deploy fails with `release_failed` before it changes anything when the tag cannot be made; the GitHub release is best effort (the `release` step says when it could not be made, and the next deploy of the commit makes it). A staging deploy never makes the release of a final version, and `bump` is refused outside production. Versions are cut under one lock per repo. Known limit: the tag list is read in full on every deploy and refuses a repo with more than 5000 tags (`github.ErrTooManyTags`) rather than work from a partial list; prune old `-rc` tags or change the lookup before a service gets there. Forge itself is released by pushing a `vX.Y.Z` tag to `showmino/forge` (`release.yml`, goreleaser: CLI binaries and `ghcr.io/showmino/forge-api:vX.Y.Z`).
- **Deleting a service (2026-10-11):** `DeleteService` takes down what the service runs before it leaves the catalog (`internal/server/service_teardown.go`, wired with `catalog.EnableTeardown`): previews are destroyed, then production and staging are removed (the values file leaves forge-deploys, Argo CD removes the application and its workloads, forge-api deletes the namespace if it is Forge's), and the catalog entry goes last. With anything to take down it is an operation of kind `delete_service` on `services/<svc>`; a service that runs nothing is removed at once. While it runs the service is marked as being deleted (`Catalog.refuseDeleting`): no deploy, preview or resource run can start for it, and its deploy targets are locked. It never touches a namespace or an Argo CD application without Forge's labels, keeps the GitHub repo, and every step can be repeated, so a failed or cancelled delete is run again; a cancel after the values left the deploy repo says that Argo CD still takes the service down. `validate_only` returns what would be taken down (`removes`), which the CLI prints before it asks. Not removed: the repo, its images in ghcr.io, and the deploy history in forge-deploys (a new service of the same name would see the old commits in `deploy history`).
- **Teams (2026-10-11):** `TeamService.ListTeams` and `forge team list` read the organization's teams from GitHub as the App (`internal/server/teams.go`, one-minute cache). The App needs the organization permission "Members: read" (granted by the owner on 2026-10-11; live on k3s at forge-api 57a118e); without it the RPC answers FAILED_PRECONDITION naming the permission. ## Common mistakes

- Running lint with an older golangci-lint than CI's v2.14.0 (it cannot read Go 1.27 export data), or "fixing" the two `G117` nolints in `internal/auth/store.go`: storing the refresh token is intended; encrypting the file fallback is the real follow-up.
- Following the README's `k3s ctr images import` path on the demo cluster: the dev machine is not a node.
- Exposing Dex through Istio `*.showmino.com`: it is public, and its GitHub OAuth App callback must match that host.
- Adding a package-level variable or calling `os.Exit` outside `main`.
- Giving a CI workload a new RPC by adding a permission: workloads pass the interceptor only for the procedures in `workloadProcedures` (`authn.go`), and each of those handlers must call its `ci_scope.go` check.
